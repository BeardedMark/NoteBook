## Базовый формат (рекомендую)

**`MAJOR.MINOR.PATCH`**  
Пример: `2.4.1`

- **MAJOR** — ломающие изменения  
    API, формат данных, поведение, совместимость.
- **MINOR** — новые фичи без поломок  
    Расширение возможностей.
- **PATCH** — багфиксы и мелкие правки  
    Без изменения контрактов.
    

---

## Расширенный формат (4 цифры)

**`MAJOR.MINOR.PATCH.BUILD`**  
Пример: `2.4.1.37`

- **MAJOR** — ломающие изменения
- **MINOR** — новые фичи
- **PATCH** — багфиксы
- **BUILD** — номер сборки / деплоя / CI-инкремент  
    Меняется на каждый билд, не имеет продуктового смысла.
    

> Альтернатива, если хочешь 4 смысловых уровня:  
> **`MAJOR.MINOR.FEATURE.PATCH`**  
> Пример: `1.3.2.5`  
> (но это хуже читается и путает ожидания)

---

## Предрелизы

Формат:  
`1.3.0-alpha.1`  
`1.3.0-beta.2`  
`1.3.0-rc.1`

Используй для тестирования и нестабильных версий.

---

## 4. Когда что повышать

|Ситуация|Что менять|
|---|---|
|Исправил баг|PATCH|
|Добавил фичу|MINOR|
|Убрал метод / сломал контракт|MAJOR|
|Рефактор без внешних изменений|PATCH|
|Новый деплой / билд|BUILD|

---

## MVP и нестабильные версии

Пока продукт нестабилен:
- `0.x.y` — активная разработка
- `0.1.0` — первый MVP
- `0.5.0` — почти готово
- `1.0.0` — первый стабильный релиз

## Практика для реального продукта

**В коде / API:**
- Строгий SemVer: `1.4.2`
- Или: `1.4.2+build.37

**В Git:**
- Теги: `v1.4.2`
- Ветки: `release/1.4`

**В UI:**
- Показывать: `v1.4`
- Не показывать: `.37

**Документация:**
- `CHANGELOG.md` с разбивкой по версиям

---

## Мини-правила, чтобы не было хаоса
- У каждой цифры одно значение
- BUILD не влияет на совместимость
- MAJOR меняется редко
- Не меняй несколько уровней за раз
- Не показывай BUILD пользователям
- Все версии — через теги и changelog

## Рекомендуемая схема для твоих проектов

**WebMMO / SaaS / коробка:**
- Разработка: `0.x.y`
- Релиз: `1.0.0`
- Фичи: `1.1.0`, `1.2.0`
- Багфиксы: `1.2.1`
- Билды: `1.2.1.45`
